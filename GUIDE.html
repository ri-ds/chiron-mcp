Field guide

Chiron MCP

Sixteen tools that let Claude explore your Chiron research warehouse — find variables, build a patient cohort, count it, and pull rows — without anyone writing SQL.

What it is

Chiron is a cohort-discovery tool for human-subject research data. A researcher picks filters to describe which patients and which columns, and Chiron compiles that into one query against a clinical warehouse. This server exposes that machinery to Claude, so the picking can happen in conversation.

Metadata database The data dictionary

Dataset → Collection → Concept, stored as database rows. Describes the shape of the data and who may see it. No patient rows live here.

Warehouse The patient data

A separate Postgres, one schema per dataset, with tables generated at runtime from those dictionary rows. Reached only through SQLAlchemy.

Everything you build is two JSON documents: a cohort_def (who is in) and a table_def (what columns). The server is stateless — every tool takes a cohort_def and hands one back, so Claude holds the working query and Chiron keeps none of it. Nothing you do here touches a researcher's saved workspace.

A real session

Every number below is an actual result from synthea-10k, not an illustration.

  1. "What datasets can I look at?" chiron_datasets
    3 accessible
  2. "How many patients in synthea-10k?" chiron_count_cohort · empty cohort = everyone
    10,000
  3. "What conditions are most common?" chiron_concept_values · condition__description
    obesity 2,421 · hypertension 2,134
  4. "Build me a cohort of asthma patients." chiron_describe_concept → chiron_edit_cohort
    cohort_def returned
  5. "How many is that?" chiron_count_cohort
    838 of 10,000
  6. "Show me their diagnoses and dates." chiron_run_table · description, start
    829 records · 838 subjects

Step 4 matters most. Chiron publishes no machine-readable schema for filter inputs — a filter is submitted as HTML form field names like selected_categories or cd_numeric_min, and which one applies depends on the variable's type. chiron_describe_concept is the only thing that answers that, which is why Claude calls it first.

Who can see what

Access is not a login check — it's a per-(user, dataset) record carrying one of three levels. Because this server calls Chiron's Python directly rather than its web API, three checks that live only in the web layer are re-implemented and applied on every call.

LevelPatient rowsCounts & crosstabsMeaning
phi yes yes Identifiable data. Opt-in only — the ceiling defaults to deid.
deid yes yes De-identified. PHI variables are swapped for their de-identified form automatically.
agg refused yes Aggregate only. Row-level tools refuse outright, matching Chiron's own behaviour.
  • It never grants access. Chiron's web UI quietly creates an access record the first time you touch certain datasets — at phi level on the synthea ones. This server refuses instead and tells you what to create deliberately.
  • An errored cohort is never run. A broken definition collapses to an empty one, and an empty cohort means every patient. The server refuses rather than silently returning the whole dataset.
  • A failed filter returns no reusable cohort. It hands back unchanged_cohort_def under a different name, so a failure can't be chained into an accidental whole-dataset query.
  • It is read-only. No saved report is written, no ETL runs, no schema changes.

Setup

Already registered in Claude Desktop. It appears after a restart.

"chiron": {
  "command": ".../chiron-mcp/.venv/bin/python",
  "args": ["-m", "chiron_mcp.server"],
  "cwd": ".../chiron-mcp",
  "env": {
    "CHIRON_MCP_USERNAME": "demouser",
    "CHIRON_MCP_MAX_ACCESS_LEVEL": "deid"
  }
}

To check the connection before debugging anything else:

CHIRON_MCP_USERNAME=demouser .venv/bin/python scripts/harness.py

To open another dataset to an account:

.venv/bin/python scripts/grant_access.py \
    --user demouser --datasets synthea-10k --level deid

Known limits

  • Regex text filters are broken upstream. Chiron's own tests document /slash-wrapped/ terms as returning wrong answers. Avoid them.
  • Terms absent from the data are rejected. Pass ignore_warnings to accept a filter anyway — useful for values that exist in one dataset but not another.
  • Most variables are multi-value. They live in their own lookup table, so a filter matches a patient if any of their values match. "No white race value" and "a non-white race value" are different questions.
  • Crosstab returns preformatted text, not structured rows — that's what Chiron's analysis engine hands back.
  • Saving isn't implemented. There's no way to push a cohort back into the Chiron UI yet.
